# 学生档案旧表单覆盖修复

## 问题与行为

以前，服务端收到保存请求后重新读取档案，再将此时的档案作为条件更新旧值。这只能保护服务端读取与写入之间的竞争，不能识别页面打开后他人已保存的修改。

现在页面保留查询响应中的完整原始 StudentRecord，保存时同时发送原始快照和修改后的档案。新旧快照不匹配时返回 CONFLICT，拒绝整次更新；页面保留用户输入、禁用保存并提示重新查询或刷新。成功查询后替换原始快照并允许保存。不会自动重试或把服务端最新数据当成旧快照。

## 协议与兼容

- 新消息：`STUDENT_UPDATE_V2`。
- 新 DTO：`StudentUpdateV2Command(token, record, expected)`；新旧档案必须非空且学号一致，反序列化后再次校验。
- expected 是打开表单时的完整快照，不是权限凭据。身份仍由 token 推导，学生仍只能更新当前绑定的本人联系方式，教师仍禁止读写学生档案。
- 复用 StudentProfileSnapshot.matches 和现有 Repository 条件写入，无新增数据库字段。Access 在同一 UPDATE 的 WHERE 中比较旧字段；服务端预检后再次发生变更也不能覆盖。
- 不改变原 StudentUpdateCommand 的字段和 serialVersionUID。旧 `STUDENT_UPDATE` 对已有档案的更新返回 CONFLICT，提示升级客户端；原管理员建立不存在档案的路径仍只执行条件插入，不能覆盖同学号已存在的记录。
- 新客户端不回退到无快照保存。客户端、common、student-management 与 server 应配套更新；旧客户端查询继续可用。
- 快照比较提供当前字段值相等时的条件保存，不是单调递增的历史版本号；若数据发生变化后又完整恢复原值，不作为冲突。

## 权限与毕业约束

学生先校验当前档案归属，再比较原始快照和可修改字段；不能用伪造快照更新他人资料或只读字段。管理员继续检查 STUDENT_WRITE。毕业状态变更仍需教务毕业流程；旧表单在毕业前加载、毕业后提交时返回冲突，毕业状态和既有修改保持不变。

## 验证范围

- 两名管理员交替提交：旧姓名不能覆盖新姓名。
- 管理员先修改，学生旧表单随后提交；学生两份旧联系方式表单交替提交。
- 重新加载后可成功保存；冲突时页面保留编辑内容并要求重载。
- 内存和真实临时 Access 库、失效 token、越权、伪造只读字段、旧客户端更新拒绝。
- 复用并迁移既有保存与毕业并发测试，覆盖服务端校验后状态再变更。
- 真实 Socket 序列化经过 RemoteStudentService 与 ServerApplication.dispatch，验证 V2 分发、快照保存及刷新后的成功重试。
