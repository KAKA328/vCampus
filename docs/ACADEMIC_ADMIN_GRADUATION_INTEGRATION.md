# 学籍三角色职责、学分审查与毕业管理

核对日期：2026-09-06。以本文件为本轮职责基线，替代旧文档中“尚无学生学分查询、尚无教务毕业管理”的描述。

## 1. 角色与范围

| 角色 | 信息查询 | 审查与管理 |
|---|---|---|
| 学籍教务管理员 ACADEMIC_ADMIN | 全部学生完整档案、全部教师档案（含非在职），指定学生课程历史与当前学分 | 维护学生档案；填写适用要求学分、选填审查说明并保存学分审查；查看历次记录；人工核查其他条件后办理毕业 |
| 学生 STUDENT | 本人档案、本人课程历史、待重修、当前累计学分 | 无教务审查、他人档案、毕业办理权限；原本人联系方式维护权限保留 |
| 教师 TEACHER | 本人工号、账号、姓名、院系、职称与在职状态 | 全部只读；不能查看授课学生档案或学生成绩 |
| 系统管理员 ADMIN | 保留教务查询与办理能力，便于维护和验收 | 与教务使用相同审查和毕业规则 |

“全部人员”在学籍领域是全部学生与教师档案。账号密码、登录安全、其他岗位账号管理继续归用户管理模块，不向教务暴露密码哈希或赋予用户管理权。

## 2. 页面入口

- 教务：学籍管理 → 学生档案维护 / 全员信息与毕业管理。点击“全部学生”或“全部教师”；选中学生行可填入目标学号，也可手动输入学号。完整字段较多，可水平滚动。
- 学生：学籍信息 → 成绩与重修 → 当前学分。无须输入学号，服务端按本人会话查询。
- 教师：学籍查询 → 我的教师信息。只读本人资料，非在职状态不阻止有效登录账号查询本人。

## 3. 统一学分口径

`CreditSummary.from(studentId, history)` 是新学生查询、教务查询/审查及原内存/Access 实时审查共同使用的计算入口：

1. 按课程号去重，同课程多个通过记录取最高 `earned_credits`，计一次课程学分；保持当前项目既有聚合选择。
2. 未通过记录不贡献学分；修复原实现可能把失败记录中较高学分带入同课程已通过汇总的问题。
3. 当前待重修课程数是不存在任何通过记录的课程数；历史重修课程数是曾出现第 2 次以上尝试或“重修”标记的课程数，两者独立。
4. 返回累计学分、通过课程数、当前待重修数和历史重修数，不返回毕业结论。学生查询不会创建审查快照。
5. NULL 分数仍返回数据错误，不当成 0；课程成绩仍以现有 tblCourseResult 为输入。审核状态字段尚未落地，本次没有实现 APPROVED 过滤。

同课程改用“最新通过”还是“最高通过”、特殊学分/免修仍需统一业务契约；确认后只改公共聚合入口，并补内存/Access 测试。

## 4. 教务学分审查与毕业办理

### 保存审查

教务选定学生，填写正整数“要求学分”；“审查说明（选填）”可留空，也可备注适用专业、年级或培养方案。系统从服务端数据库重算学分，保存完整统计、要求学分、依据、操作人、时间，以及学生档案和每条课程尝试的指纹。

本阶段没有自动从培养方案推导毕业要求的正式契约，因此要求学分由有权限教务依据适用规则填写；学生不能提交或修改此数值。系统拒绝 0 或负数要求学分。

### 确认毕业

- 必须使用该学生最新的审查记录；审查已达到要求学分且当前待重修为 0。
- 学生当前状态必须为“在读”；重复毕业办理、休学/退学等状态均拒绝。
- 成绩任一尝试或学生档案发生变化，即使总学分相同，也拒绝旧记录，要求重新审查。
- 教务必须勾选已核查培养方案、必修/选修及其他毕业条件，再确认弹窗；审查说明可留空。
- 服务端记录毕业操作人、时间和说明，并将 tblStudent.status 改为“毕业”。两处写入使用同一 Access 连接和事务，任一写入失败回滚全部变化。
- 普通 STUDENT_UPDATE 不允许直接设置或撤销“毕业”，避免绕过审查链。已毕业学生其他档案字段仍可按原教务权限维护。

这实现的是教务人工确认的毕业管理，学分达标仅是必要检查，不宣称系统已自动验证所有毕业条件。当前不提供毕业撤销、证书编号、延期申请等流程；如果要支持，需要保留原决策并新增带原因的纠正流程，不能覆盖历史记录。

## 5. 消息与服务接口

### 学生本人

`STUDENT_ACADEMIC_QUERY_V1 + StudentAcademicQueryV1Command(token, CREDITS)` → `OK + CreditSummary`。

HISTORY / PENDING_RETAKES 原语义不变。新枚举值为新增查询能力，旧客户端不使用它；升级时客户端、common、student-management、server 配套部署。

### 教务

`ACADEMIC_ADMIN_V1 + AcademicAdminCommandV1`：

| Action | 参数（除 token） | 成功数据 |
|---|---|---|
| STUDENTS | 无 | List<StudentRecord>，全部学生 |
| TEACHERS | 无 | List<TeacherProfile>，全部教师 |
| HISTORY | studentId | List<CourseHistoryRecord> |
| CREDITS | studentId | CreditSummary |
| ASSESSMENTS | studentId | List<AcademicAssessment>，最新在前 |
| REVIEW | studentId、requiredCredits、note（选填） | 保存的 AcademicAssessment |
| GRADUATE | studentId、assessmentId、note（选填）、otherRequirementsConfirmed=true | 包含毕业操作信息的 AcademicAssessment |

操作人不能由客户端指定，由 token 当前会话推导。服务端先检查 ADMIN/ACADEMIC_ADMIN 角色，查询要求 STUDENT_READ，REVIEW/GRADUATE 要求 ACADEMIC_REVIEW。其他角色即使伪造命令也被拒绝。

失效会话 UNAUTHORIZED；角色/权限不足 FORBIDDEN；参数错误 BAD_REQUEST；学生不存在 NOT_FOUND；过期审查、学分不足、非在读、重复办理 CONFLICT；数据库失败 SERVER_ERROR。列表无数据返回 OK + empty list。

`StudentManagementService.findAll()` 和 `TeacherProfileService.findAll()` 是服务端内部能力，只经上述受保护消息向教务开放。教师本人的 TEACHER_SELF_QUERY_V1 仍严格限本人，不以新增教务目录扩大教师权限。

## 6. 数据库与部署

新增 `tblAcademicAssessment`，由学籍教务功能负责写入。COUNTER 字段 `assessment_order` 用于稳定排序，UUID `assessment_id` 为主键；包含完整学分统计、要求学分、指纹、审查依据与操作人，以及毕业确认信息。

原 `tblAcademicReview` 保留兼容；本轮新页面使用新完整快照表，不把旧表“部分历史快照、部分当前统计”当作新审查记录。原表原有 Service 不用于新毕业确认。

**部署须使用最新 schema.sql + seed.sql 重建测试/验收数据库，或者由维护人员另行设计受控升级；旧库没有新表，教务审查会报错。** 本次仅在临时数据库验证，没有删除或重建用户原有数据库，也没有自动迁移历史快照为有效新审查。

Access 模式重启保留审查和毕业记录；无 --db 的内存模式仅作演示，重启数据消失。

## 7. 与选课模块的接续要求

- 正式成绩仍由选课/教务成绩模块写入；学籍不写成绩或审核批次。
- 后续 result_status/source_submission_id 落地时，学籍方在 AccessAcademicReviewService.readHistory 筛选正式有效成绩，供学生查询与教务审查使用。选课重修资格保留其原实现，过滤条件由选课负责人同步，不直接改动对方代码。
- 成绩撤回/更正不得直接修改既有学籍审查快照。新毕业确认会检查指纹；已办理毕业之后的成绩更正则需要另行建立教务复核/纠正流程，当前不会自动撤销毕业。
- 审核写入端应与毕业确认协调并发事务和重新审查规则；未经联合验证不将外部直接改库作为正式工作流。
- 自动读取培养方案要求学分、自动验证必修/选修仍需选课方提供明确规则和接口。本阶段按教务填写要求学分并人工确认其余条件落地，说明可选填。
- 既有 seed 缺完整选课轮次且年级/教学班样例不匹配的问题仍存在，见 STUDENT_ACADEMIC_QUERY_INTEGRATION.md；不影响直接读取学籍成绩与教务审查。

## 审查修复：普通档案保存与毕业状态一致性

普通学生联系方式写入改用 `updateContacts(userId, expected, phone, email)`。expected为Handler从服务端读出的档案，包含账号绑定；持久化层在同一次条件更新中验证该档案仍未变化，仅更新phone/email。期间若毕业、账号重绑或其他档案变化，返回CONFLICT，客户端需刷新重试。

教务普通档案更新改用 `saveIfUnchanged(record, expected)`，数据库以原档案字段作为UPDATE条件，防止旧请求覆盖并发写入的毕业状态。expected为空表示仅新增，已有同学号时返回CONFLICT，不退化为upsert。原内部save继续用于初始化及受控业务流程，不由学生/教务普通更新请求直接使用。

内存实现提供同样的比较并写入语义；Access使用参数化条件UPDATE，不仅在Handler中重复SELECT。本轮补充学生/教务两种角色、内存/Access两种存储的确定性并发测试，以及账号重绑、重复创建、空字段兼容测试。


说明可空兼容：null、空串和纯空白输入统一作为空文本保存；保留原basis列NOT NULL及现有序列化字段。填写说明时仍限制255字，毕业确认和学分检查不变。
