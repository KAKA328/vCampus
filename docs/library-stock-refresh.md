# 图书馆并发借阅后的库存自动刷新

## 问题与修复范围

基于 `origin/main` 的 `a249845c8e4113cd28d8dbe701a0f9b520ba23ba`，在独立分支 `fix/library-stock-refresh` 完成客户端修复。

原先服务端拒绝借阅后，客户端显示失败提示便返回，只有成功路径重新查询馆藏，因此抢最后一本失败的客户端仍可能显示旧余量。库存写入继续由原服务端的事务与并发控制负责，本次没有改变服务端、数据库、DTO 或消息协议。

## 刷新行为

- 借阅请求结束后，无论成功、业务拒绝还是网络异常，都安排一次只读库存核对；不会自动重试借阅。网络异常时操作可能已执行，应核对借阅记录后再决定是否重新提交。
- 馆藏页可见且已加载成功时，每 5 秒触发后台查询；切换页签或模块、关闭窗口后停止轮询，重新显示时补查。
- 这属于定时轮询，不是服务端推送。其他客户端的变动在下一次查询完成后显示，实际延迟受网络耗时及当前操作影响。
- 后台查询使用上次已展示的筛选条件，不使用未提交的搜索草稿；保留选中图书、排序、滚动位置和业务失败提示。列表内容没变时不重绘。
- 同一页面最多一个后台查询，忙碌期间合并重复请求；旧响应不能覆盖后续前台操作的结果。后台查询不禁用按钮。
- 选择多行、展开分类或使用模态对话框时暂缓刷新。网络异常保留原数据并独立提示；会话或权限失效时暂停轮询。
- 表格下方独立显示最近同步时间及自动刷新状态。

## 实现位置

- `LibraryCatalogRefresh`：页面生命周期、计时器、只读后台查询、请求合并和响应代次校验。
- `LibraryCatalogSelection`：按图书编号恢复选择、保留排序与滚动、避免无变化重绘。
- `LibraryCatalogActions` / `LibraryRequestRunner`：借阅前登记核对，前台请求结束后执行。
- `LibraryViewData`：正常加载与安静刷新共用数据投影逻辑。
- `LibraryPanel` / `LibraryViewBindings` / `LibraryWorkspaceLayout` / `LibraryViewState`：可见性绑定及同步状态展示。

## 多机复核步骤（待小组执行）

1. 保留同一台服务端和同一份独立测试库，各客户端替换为本次新 JAR；不同人员使用不同账号。
2. 选择只剩 1 册可借的同一本图书，让甲、乙两端均查询并看到余量 1。
3. 两端同时借阅：预期仅一端成功，另一端保留借阅失败提示，查询完成后余量更新为 0。
4. 第三端只停留在馆藏页，不点击查询：应在下一次自动查询完成后看到余量 0，同步时间更新。
5. 成功借阅方归还后，其他馆藏页同样应自动显示余量 1。
6. 保持筛选、排序、多行选择及滚动位置，确认库存变化没有清空这些状态，也没有覆盖操作提示；输入但不提交的新关键词不应改变后台查询范围。
7. 切走馆藏页确认不继续轮询；返回时核对新余量。断网时保留旧数据并提示刷新不可用，恢复后仅重试查询，不应新增借阅记录。
