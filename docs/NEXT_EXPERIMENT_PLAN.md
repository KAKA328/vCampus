# 后续实验推进计划

> 本计划基于 2026-08-26 GitHub 最新 `main` 整理，用于指导后续编码、联调和验收准备。

## 实验 E1：主线同步与安全分支

- 从最新 `main` 新建短期功能分支，不在旧分支上继续叠加改动。
- 每次合并前运行 `mvn clean test`。
- 修改公共协议、角色权限、数据库字段时，必须同步更新 `docs/INTERFACES.md`、`docs/PERMISSIONS.md` 和 `database/README.md`。
- 合并其他子系统 PR 前，把“是否新增 `MessageType`、权限、跨模块接口、服务器 Handler、客户端调用和测试”作为固定流程点；缺一项不直接进 `main`。

## 实验 E2：用户会话与重复登录

- 当前状态：已完成代码与自动化测试。
- 同一账号同一时间只允许一个活动会话。
- 已登录账号再次登录时返回 `CONFLICT`。
- 用户登出、自注销或管理员注销后释放活动会话。
- 补充自动化测试，覆盖重复登录、登出后重新登录、注销后 token 失效。

## 实验 E3：GUI 布局与主界面优化

- 当前状态：已完成首页卡片自适应换行和滚动区域，并将开户注册入口收敛到管理员端；后续需要继续美化各子系统页面。
- 登录、管理员开户注册、主界面使用统一字体、颜色、按钮和间距。
- 首页模块卡片说明文字随窗口宽度换行。
- 首页内容区域支持滚动，避免窗口缩放后卡片显示不全。
- 管理员开户注册窗口允许调整大小；后续模块页面统一采用“标题区 + 查询区 + 表格区 + 操作区 + 状态栏”。

## 实验 E3.5：用户批量导入后端闭环

- 当前状态：已完成后端服务、Socket 消息、Access 字段、迁移脚本、接口文档和自动化测试；暂不接入 Swing 页面，减少与后续客户端/子系统 PR 的冲突。
- 管理员通过 `USER_IMPORT` 提交 `UserImportCommand(token, rows)` 批量开户注册。
- 服务端统一校验 `USER_MANAGE`，普通学生、教师和其它无权限角色不能导入账号。
- 每个成功导入账号记录 `created_by`、`created_at`、`import_batch_id`，并写入 `IMPORT_USER` 审计事件。
- 单行账号重复或数据非法时，仅在 `UserImportResult.failures` 中返回该行失败，不影响同批次其它有效账号。
- 后续如需做页面，建议单独开 UI PR，只新增管理员端 Excel/CSV 表格导入入口，不改学生、选课、图书馆、商店页面。导入源文件只是账号清单，最终数据仍写入 Access 数据库。

## 实验 E3.6：管理员用户管理页优化

- 当前状态：已完成管理员用户管理页拆分与美化，入口工作台布局保持不变；批量导入正从手工填表改为选择外部 Excel/CSV/TSV 文件后预览并导入。
- 用户管理页采用“顶部说明 + 左侧单账号开户注册卡片 + 右侧批量导入表格卡片”结构。
- 左侧卡片保持紧凑宽度，右侧批量导入区域随窗口放大，表格区域负责承接主要空间，避免窗口比例变化时内容拥挤。
- 批量导入支持选择 `.xlsx`、`.csv`、`.tsv` 文件，要求包含账号、姓名、初始密码和角色列。
- 预览表只显示账号、姓名、角色和导入结果，不显示初始密码；确认后通过 `USER_IMPORT` 写入 Access 数据库。
- 本次 UI 只接入用户管理页，不修改学生、选课、图书馆、商店页面，降低后续子系统 PR 冲突。

## 实验 E4：学籍档案与学业审查数据

- 当前状态：已完成学生基础档案字段、历史课程记录、Access 查询、服务器身份映射和 Swing 页面；`AcademicReviewService` 已提供实时审查与最新快照读取，后续需要在真实验收库上验证迁移和端到端权限。
- 账号由系统管理员创建、批量导入或由初始化脚本预置；学生/教师档案可以先由对应子系统导入或维护，再通过 `student_id` / `teacher_id` 绑定 `user_id`。
- 学生基础信息由 `tblStudent` 保存，并通过 `user_id` 与账号关联。
- 教师基础信息由 `tblTeacher` 保存，并通过 `user_id` 与账号关联。
- 历史选课、首修、重修、成绩、是否通过和获得学分由 `tblCourseResult` 保存。
- 学业审查结果由 `tblAcademicReview` 保存，统计累计学分、挂科门数、重修门数和毕业条件。
- 账号未关联学籍档案时，客户端提示“暂无学籍档案，请联系学籍管理员维护”。

## 实验 E4.1：账号与学生/教师档案绑定方案

- 当前目标：先完成对接规范和接口边界确认，再进入具体页面和数据库读写实现，避免用户管理、学籍管理和选课模块重复维护同一批字段。
- 已确定身份模型：`user_id` 为登录身份，`student_id` 为学生学号，`teacher_id` 为教师工号。
- 推荐流程：先有学生/教师档案，再由管理员创建或导入账号，最后通过 `student_id` / `teacher_id` 绑定 `user_id`。
- 学生本人业务流程统一由服务器根据 `token -> user_id -> student_id` 定位档案；教师本人业务流程统一由服务器根据 `token -> user_id -> teacher_id` 定位档案。
- 商店订单和图书借阅继续直接使用 `user_id`，不要求学生或教师额外输入学号/工号。
- 对接规范见 [`ACCOUNT_PROFILE_INTEGRATION.md`](ACCOUNT_PROFILE_INTEGRATION.md)，后续新增绑定接口或消息类型时同步更新 `docs/INTERFACES.md`、`docs/PERMISSIONS.md` 和 `database/README.md`。

## 实验 E4.2：账号绑定接口与页面入口

- 管理员端补充学生账号绑定和教师账号绑定入口，可按账号、学号或工号查询待绑定对象。
- 绑定前校验账号角色、档案存在性、是否已绑定其它账号和当前操作者权限。
- 绑定成功后，学生进入学籍和选课页面时不再手工输入学号；教师进入授课或成绩页面时不再手工输入工号。
- 未绑定档案时，相关页面显示可理解的提示，不自动凭账号创建历史成绩、课程结果或授课关系。

## 实验 E5：选课管理与成绩录入

- 教务管理员实现开课、修改容量、停课。
- 任课教师只能录入本人授课课程的成绩。
- 教务管理员可复核成绩并触发学业审查。
- 服务器端必须校验 `COURSE_MANAGE`、`GRADE_WRITE`、`ACADEMIC_REVIEW` 以及授课/学籍数据范围。

## 实验 E6：五模块联调

- 学籍、选课、图书馆、商店、用户管理均接入服务器 Handler 和客户端 Swing Panel。
- 每个模块至少包含正常流程、异常流程和权限拒绝流程。
- 学生、教师、教务管理员、图书管理员、商店管理员、系统管理员分别使用不同演示账号验收。
